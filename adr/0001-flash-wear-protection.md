# ADR 0001. Защита флеш-накопителя от преждевременного износа

- **Статус:** Принят (2026-09-27)
- **Область:** Home Assistant на одноплатнике с eMMC или SD-картой

## Контекст

Флеш-память выдерживает ограниченное число перезаписей. Home Assistant пишет
непрерывно: recorder (база истории состояний) сбрасывает данные на диск каждые
5 секунд по умолчанию, журналы системы и дополнений идут потоком, а журнал
файловой системы ext4 усиливает каждую мелкую запись. На типичной установке
это гигабайты в сутки; износ виден в регистрах eMMC (`life_time`) задолго до
отказа. Отказ накопителя — это потеря всей установки, поэтому дешевле платить
дисциплиной записи, чем восстановлением.

Диагностика перед любыми изменениями (всё — только чтение):

```sh
# износ eMMC: 0x01=0–10%, 0x02=10–20% … ; pre_eol 0x01 = норма
cat /sys/block/mmcblk*/device/life_time /sys/block/mmcblk*/device/pre_eol_info
# сколько записано с загрузки (поле 10 — секторы по 512 байт)
awk '$3 ~ /^(mmcblk[0-9]+|sd[a-z])$/ {printf "%s: %.1f GiB\n", $3, $10*512/2^30}' /proc/diskstats
# главные писатели
for p in /proc/[0-9]*; do wb=$(awk '/^write_bytes/{print $2}' $p/io 2>/dev/null); \
  [ "${wb:-0}" -gt 100000000 ] && echo "$wb $(tr -d '\0' <$p/cmdline | cut -c1-60)"; done | sort -rn | head
# самые «болтливые» сущности recorder за сутки
sqlite3 -readonly home-assistant_v2.db "select m.entity_id, count(*) n from states s \
  join states_meta m on s.metadata_id=m.metadata_id \
  where s.last_updated_ts > strftime('%s','now')-86400 \
  group by 1 order by n desc limit 25"
```

## Решение

1. **Сначала замер, потом настройка.** Зафиксировать базовую точку (счётчик
   секторов + `life_time` + дата) и найти реальных писателей. Типичный вывод:
   85% строк базы дают несколько сущностей, а вовсе не «все устройства».
2. **Журналы и подкачка — не на флеш.** `/var/log` и swap держать на zram
   (сжатый диск в памяти; в Armbian это штатно — не ломать). Журнал systemd
   **не** переводить в persistent на флеш; если нужны пост-мортемы — пересылать
   журнал на внешний приёмник (syslog, systemd-journal-upload, Loki).
3. **Recorder — главный управляемый писатель:**
   - `commit_interval: 30` (реже fsync → меньше усиления через журнал ФС);
   - `exclude` для найденных замером болтунов. Классика: `sun.sun`,
     автоматизации-опросники (каждый запуск пишет строку), технические
     сенсоры розеток (вольты/амперы/уровень сигнала). Полезную историю
     (энергия, температуры, состояния) не исключать;
   - `purge_keep_days` оставить умеренным (10 по умолчанию);
   - помнить: `exclude` recorder не влияет на выгрузку во внешние базы
     (интеграция influxdb/VictoriaMetrics получает всё).
4. **Файловая система:** `noatime`, `commit=600` для ext4, включённый
   `fstrim.timer`. В готовых сборках (Armbian) обычно уже так — проверить,
   а не настраивать вслепую.
5. **Выключить неиспользуемые пишущие службы** (учёт трафика vnstat и
   подобные «мелкие, но каждые 5 минут»).
6. **Контроль:** через сутки повторить замер (разница счётчиков), регистр
   износа включить в мониторинг и смотреть раз в квартал.

## Последствия

Плюсы:
- объём записи падает в разы почти без потери функций;
- ресурс накопителя растягивается соразмерно; есть базовая точка для контроля.

Минусы и цена:
- при внезапной потере питания теряется до `commit_interval` (30 с) последней
  истории — для домашней истории приемлемо, но это осознанная плата;
- история исключённых сущностей недоступна в HA (графики по ним пусты);
- журналы на zram живут до перезагрузки: без внешней пересылки пост-мортем
  после падения питания невозможен — решение о пересылке принимать отдельно;
- разовый перезапуск ядра HA для применения настроек recorder.

## Связанное

- Диагностика «кто пишет» и запрос болтунов — выше в «Контексте».
- Локальные ADR проектов фиксируют конкретные цифры замеров и списки exclude.
